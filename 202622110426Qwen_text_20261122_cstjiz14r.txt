## ITEM 2 — S8b CALIBRATION & SPILL-BAND: CONFIRM, with one measurement precision
Accept the correction: my earlier "66 chars" (and the HTML's 70) was wrong; it
came from the prototype placeholder, not the real screenshots. Verified bounds:
Dialogue/Story = 50 digits × 3 lines; Box 0 Summary = 47 digits × 5 lines.
CRITICAL precision (keeps us honest to D13 "measure rendered width"):
- The digit string is a RULER to set pixel width, NOT a character law. Digits are
  ~half-width; JP glyphs are ~full-width. A box calibrated to 50 digits will wrap
  Japanese at roughly ~25 chars. Therefore the overflow decision MUST come from
  actual wrapped-line counting (txt.count(...,"displaylines")), never from a
  char-count threshold. tkFont.measure("1234567890"*5) sets the width; displaylines
  decides overflow. This is exactly the proposed design — good.
- The existing editor badge `_update_rendered_char_count` uses a 45-char/line
  heuristic. That is a SEPARATE, crude heuristic. Do not conflate it with the
  preview's pixel/displaylines overflow. Unifying them is a later measure-first
  item; for S8b the preview badge uses displaylines, the editor badge stays as-is.
- displaylines requires a mapped, laid-out widget: compute once per render after
  update_idletasks(), not per keystroke (preview is read-only → renders once per
  box change). Zero new after() timers, zero idle CPU — confirmed feasible on
  Tk 8.6 (Python 3.12 Windows).
Spill-band design CONFIRMED: fixed pixel width; ▼ + gold border pinned at line 3
(Dialogue) / line 5 (Box 0); overflow expands into a bounded red-tinted band
(~6–7 lines, scrollbar fallback); badge "⚠ OVERFLOW: 4/3 lines"; 100% selectable/
copyable; never truncated. Story Preview = lightweight fixed-width tk.Frame cards,
no per-card Canvas. Box 0 Summary skin = Preview-mode-only (user confirmed).
VERDICT: CONFIRM calibration + spill-band, with the digits≠JP-width precision above.
