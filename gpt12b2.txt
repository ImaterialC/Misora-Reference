## **1. S11b v1.4.11 — closure dan 1-line&#x20;**`ProjectDiffDialog`

**Keputusan: ACCEPT perubahan satu baris dan APPROVE penutupan S11b untuk local commit**, dengan satu smoke test GUI sebelum commit.

Alasan teknis:

- `THEME` yang diimpor dari `assets/icon.py` adalah dictionary palette datar. Tidak ada key `"dark"`. [Source](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/assets/icon.py?utm_source=chatgpt.com#L11-L25)
- Ekspresi lama `getattr(parent, "theme", THEME["dark"])` mengevaluasi `THEME["dark"]` sebelum pemanggilan `getattr()`. Karena key itu tidak ada, `KeyError` dapat terjadi meskipun `parent.theme` sebenarnya tersedia.
- `MisoraApp` memang menginisialisasi `self.theme` sebelum dialog digunakan. Penggunaan `getattr(parent, "theme", None) or THEME` karena itu mengambil theme aktual aplikasi dan menghindari evaluasi default yang bermasalah. [Source](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/misora.py?utm_source=chatgpt.com#L2066-L2079)

Saya menerima perubahan tersebut sebagai **bounded incidental bugfix**, bukan sebagai izin untuk memperluas scope S11b.

Ada satu kekurangan pengujian yang perlu diperhatikan: tes S16 yang tersedia melakukan mock terhadap `ProjectDiffDialog`, jadi tidak benar-benar menjalankan konstruktornya. [Source](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/tests/test_p3_s16_misora_workspace.py?utm_source=chatgpt.com#L278-L283)

Sebelum commit, jalankan satu smoke test Windows: buka workspace kedua dalam keadaan ada beberapa file terbuka sehingga `ProjectDiffDialog` benar-benar dibuat. Pastikan dialog muncul, warna/layout normal, dan pilihan Cancel tetap berfungsi. Tidak perlu memperluas matriks file hanya untuk melakukan pemeriksaan ini.

## **2. S11b2 v1.4.12 — perbaikan Save Hang**

**Keputusan: APPROVE untuk dibuatkan sesi&#x20;**`/plan`**&#x20;terpisah. Belum menyetujui implementasi.**

Proposal ini memiliki dasar teknis kuat. Saya memverifikasi alur berikut pada source baseline.

### **Akar masalah sesuai struktur source**

`_sync_modified_boxes_to_xuat()` melakukan iterasi atas setiap box yang akan disinkronkan. Untuk masing-masing box, fungsi memanggil:

1. `preview_matches()`
2. `find_and_update()`

[Source `_sync_modified_boxes_to_xuat()`](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/misora.py?utm_source=chatgpt.com#L13346-L13415)

Kedua fungsi tersebut masing-masing menelusuri root dengan `rglob("*.txt")` dan membaca file yang ditemukan. [Source `preview_matches()`](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/core/xunity_sync.py?utm_source=chatgpt.com#L114-L173) · [Source `find_and_update()`](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/core/xunity_sync.py?utm_source=chatgpt.com#L175-L257)

Setelah bundle berhasil dipatch, `on_save()` memang melanjutkan ke XUAT sync. [Source](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/misora.py?utm_source=chatgpt.com#L13530-L13557)

Dengan demikian, pertumbuhan biaya secara kasar adalah:

\\[ O(B \times F) \\]

dengan \\(B\\) sebagai jumlah box yang dimodifikasi dan \\(F\\) sebagai jumlah file dictionary yang dipindai.

Untuk 20 box dan 1.815 file, terdapat potensi 40 kali traversal penuh: 20 kali preview dan 20 kali update. Ini secara struktural cocok dengan gejala UI freeze setelah log `Patched bundle`.

### **Batas klaim bukti**

Saya membedakan dua hal:

**Terkonfirmasi dari source:** traversal dan pembacaan ulang terjadi untuk setiap box, sesudah primary bundle save.

**Dilaporkan Project Lead dari reproduksi Windows:** UI membeku lebih dari 60 detik setelah bundle berhasil dipatch.

Timestamp `Opened bundle` dan `Patched bundle` menunjukkan urutan tersebut, tetapi selisih timestamp antara kedua log itu bukan pengukuran durasi XUAT sync. Belum ada timestamp khusus untuk awal dan akhir sync. Jadi saya menilai akar masalah ini **sangat kuat didukung source dan reproduksi**, tetapi durasi khusus sync masih harus diukur langsung pada S11b2.

### **Syarat yang harus masuk ke S11b2&#x20;**`/plan`

Saya setuju dengan arah single-pass batched sync. Namun, ada beberapa hal yang wajib menjadi invariant dalam rencana implementasinya.

**A. Jangan hanya memakai XuatIndex tanpa memeriksa kesetaraan normalisasi.**

Ada perbedaan penting:

- `XUnitySyncManager` sekarang menggunakan `norm_search()`, yang melakukan `game_to_xuat()`, NFKC, normalisasi dash, dan whitespace collapse.
- `XuatIndex` menggunakan `normalize_xuat_key()`, yang juga melakukan unescape dan stripping NGUI tags.

Kedua fungsi tersebut tidak identik. [Source `norm_search()`](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/core/story_ast.py?utm_source=chatgpt.com#L111-L141) · [Source XUAT index](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/core/xuat_index.py?utm_source=chatgpt.com)

Jangan mengubah semantik pencarian sinkronisasi hanya karena index sudah tersedia. Implementasi harus mempertahankan hasil pencarian lama atau menyediakan parity tests yang membuktikan bahwa perbedaannya memang disengaja.

**B. Definisikan freshness cache.**

`XuatIndex` mempunyai `file_fingerprints`, tetapi index yang dibangun sebelumnya bisa menjadi stale ketika pengguna atau program lain mengubah file XUAT.

S11b2 harus menentukan apakah akan membangun snapshot baru sekali per save, atau menggunakan cached index dengan validasi freshness yang jelas. Jangan membiarkan perubahan eksternal hilang karena index lama digunakan tanpa validasi.

**C. Batch per key dan per file, bukan per box.**

Desain yang saya rekomendasikan:

- Resolusi immutable JP key tetap berdasarkan `box.uid` dan `orig_jp_map`.
- Lakukan pencarian semua box yang berubah dalam satu proses.
- Kumpulkan hasil berdasarkan target file dan line number.
- Pertahankan conflict preview dan konfirmasi untuk translation yang memang berbeda.
- Jika beberapa box mempunyai JP key sama tetapi English baru berbeda, tangani sebagai konflik eksplisit; jangan diam-diam mengandalkan urutan iterasi.
- Satu target file hanya mendapatkan satu backup dan satu atomic write per save.
- Pertahankan BOM, encoding, line ending, escaped multiline, dan exact key whitespace.
- Jika secondary XUAT sync gagal, primary bundle save tetap berhasil dan daftar modified boxes tidak hilang agar bisa dicoba lagi.

**D. Batasi file discovery ke kontrak Q-01.**

Saya setuju dengan pemakaian strict resolver dan exclusions dari S11b. `Translation\en\Other` dan `RedirectedResources` tidak boleh dipindai sebagai dictionary. Jangan menduplikasi aturan filter dengan versi yang berbeda di `xunity_sync.py`.

**E. Test wajib bersifat struktural.**

Synthetic benchmark 20 modified boxes pada banyak file harus mengukur jumlah traversal, pembacaan, backup, dan atomic write. Assert bahwa traversal tidak berulang per box dan setiap target file hanya ditulis sekali.

Wall-clock benchmark tetap penting, tetapi angka waktunya jangan dijadikan satu-satunya assertion yang menentukan PASS/FAIL karena performa mesin berbeda-beda. Tambahkan pengukuran aktual di Windows terhadap tree Project Lead, termasuk durasi khusus XUAT sync.

Dengan syarat tersebut, saya mendukung S11b2 v1.4.12 sebagai sesi terpisah sebelum S11c. Tidak perlu membangun asynchronous bundle-save architecture untuk menyelesaikan masalah ini sekarang.

- Pass 2 melakukan iterasi terhadap `entries`.
- Pass 3 melakukan iterasi terhadap `entries`.

[Source progress denominator](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/core/xuat_cleanup.py?utm_source=chatgpt.com#L511-L524) · [Source tiga pass](https://github.com/ImaterialC/Misora-Editor/blob/c1ec40c96c18ae6e4df61d1db77ebf999114be3d/core/xuat_cleanup.py?utm_source=chatgpt.com#L531-L593)

Perhitungannya benar:

\\[ 217{,}473 \times 3 = 652{,}419 \\]

Jadi `652,419` adalah total langkah pemeriksaan untuk tiga pass, bukan jumlah entry dictionary yang sebenarnya.

Saya setuju perubahan label ke bentuk:

`Scanning XUAT entries (Pass 1/3: 68,700 / 217,473)...`

Letakkan di S11d bersama Q-09. Pastikan label tidak membingungkan pada kondisi zero-entry, cancellation di tengah pass, atau proses yang belum mencapai pass berikutnya. Tidak perlu menarik pekerjaan ini ke S11b maupun S11b2.
