PART 2 — EXACT TECHNICAL SPECIFICATIONS (`Q-02b`)
==================================================

### 1. Strict `Q-01` Data-Safety Boundary & Full DI Exclusion Alignment
- Route ALL XUAT sync file discovery AND writes strictly through the canonical `Translation\en\Text` boundary (`resolve_xuat_text_roots` semantics supporting all 6 concrete path forms including `<GameRoot>\src\BepInEx\Translation\en\Text`) AND ALL `Q-01` exclusions:
  - 5 official XUAT rule exclusions (case-insensitive `endswith`): `.font.txt`, `.resizer.txt`, `postprocessors.txt`, `preprocessors.txt`, `substitutions.txt`.
  - All legacy exclusions (case-insensitive): `.missing.txt`, `.report.txt`, `_summary.txt` (fixing the old uppercase `_SUMMARY.txt` mismatch in `xunity_sync.py`), `_warnings.txt`, and `.bak_`.
- Full DI Requirement: `misora.py` MUST inject BOTH the resolved canonical `Translation\en\Text` roots AND the authoritative exclusion predicate (`core.xuat_index._is_excluded_xuat_file`) into the `XUnitySyncManager` batch API (never maintaining a divergent copy of exclusion rules in `xunity_sync.py`).
- Hard Data-Safety Guarantee: `Translation\en\Other`, `Translation\en\RedirectedResources`, `Translation\ja\Text`, arbitrary `Text/` dirs, rule files, and `.bak_` files MUST NEVER be read for matching OR written during Save.

### 2. Match-Semantics Preservation (`norm_search` vs `normalize_xuat_key`)
- CRITICAL: `XUnitySyncManager` matches keys using `core.story_ast.norm_search()` (`game_to_xuat()`, NFKC, dash normalization, whitespace collapse), whereas `XuatIndex` uses `normalize_xuat_key()` (which also strips NGUI tags and unescapes). These are NOT identical.
- Binding Rule: Preserve `norm_search()` matching semantics during the single-pass batched sync (do NOT silently switch sync matching to `normalize_xuat_key()`).
- Prove zero behavioral drift with an explicit old-vs-new match-set parity test covering keys with NGUI tags (`[FF0000]...[-]`), `{playername}` / `{0}`, extra whitespace, fullwidth/halfwidth case, and escaped newlines (`\n`).

### 3. Explicit 5-Stage O(E + B + M) Architecture, Read-Count Strategy & Pre-Write Freshness
Target algorithmic complexity MUST be O(E + B + M) (where E = total dictionary lines read, B = modified boxes, M = matches found) — NEVER a nested B x E loop over dictionary lines:
1. Stage 1 — Single Fresh Scan (<= 1 Read Per Eligible File): Traverse validated `Translation\en\Text` roots ONCE, skipping all excluded files before opening them. Read and strictly decode each eligible `.txt` file AT MOST ONCE (capturing file metadata snapshot: `st_mtime_ns`, `st_size`, `st_ino`/`st_dev`, plus optional content hash if chosen in `/plan` — clearly state read-count strategy and honest limits of metadata vs hash check in `/plan`, without claiming metadata-only is an absolute guarantee against crafted same-size/same-timestamp edits).
2. Stage 2 — O(E + B + M) Batch Matching & In-Memory Caching: Build a `norm_search(jp_key) -> batch_target` hash lookup table across all modified boxes first, then scan each decoded dictionary line once against the lookup table. Retain matched `(file_path, line_index, raw_key, current_val)` records AND the decoded content/encoding metadata of affected files in memory so Stage 5 does NOT re-read files unnecessarily.
3. Stage 3 — Batched Conflict Confirmation:
   - Same-JP / Different-New-EN Conflict: If multiple modified boxes in the same save share the same `norm_search(jp_key)` with DIFFERENT new English strings, treat that key as an explicit batch conflict — do NOT silently pick a winner by iteration order, do NOT write that key until resolved, and keep ALL involved box UIDs in `_modified_boxes` for retry.
   - Existing Multi-File / Differing-Translation Conflict Gate: Present ONE batched conflict confirmation after all matches are known (instead of spamming per-box modals).
4. Stage 4 — Pre-Write Freshness Check: Immediately before writing each affected target `.txt` file, compare current on-disk file snapshot (`st_mtime_ns`, `st_size`, file identity — or SHA-256 if selected in `/plan`) against the Stage 1 snapshot. If the file changed externally between scan and write (e.g., during the conflict dialog), abort updating that file (never clobber external edits) and mark all boxes targeting that file as failed/retained for retry.
5. Stage 5 — Grouped Per-File Atomic Write & Granular `_modified_boxes` Outcomes:
   - Group all confirmed line updates by `target_file_path`.
   - For each affected `.txt` file passing freshness validation: apply all line updates in memory (preserving exact raw key whitespace, escaped single-line multiline value, comments, untouched lines, encoding, BOM, and CRLF/LF), create AT MOST 1 backup, and write via `write_atomic_encoded` AT MOST ONCE per save call.
   - Granular Batch Result & Retry Preservation: The batch API MUST distinguish succeeded, conflict-skipped, and I/O-or-freshness-failed boxes. In `misora.py::_sync_modified_boxes_to_xuat()`, remove ONLY truly succeeded box UIDs from `_modified_boxes`; retain conflict-skipped and failed box UIDs (including on partial multi-file write failure where File A & C succeed and File B fails) while keeping primary bundle/file save `True`/clean (`test_s2_dirty_contract::test_07`).
   - Dedicated XUAT Sync Duration Telemetry: Measure specifically `_sync_modified_boxes_to_xuat()` (excluding bundle serialization) with `time.perf_counter()` and log it in `[XUAT Sync]` (e.g., `Synced N box(es) across M XUAT file(s) in X.XXXs (scanned K files)`).
