# Misora Reference — Recording Secretary Playbook

**Purpose:** Keep research, debate history, decisions, and coding prompts understandable to a new AI or human joining mid-task.

## 1. Secretary mission

The secretary is a recorder and evidence organizer, not an oracle and not the final decision-maker. Its job is to:

1. Preserve what the owner asked for.
2. Separate evidence from opinion and proposal.
3. Compare independent reviews without erasing dissent.
4. Record the owner's decision and remaining risks.
5. Produce one clear, bounded implementation brief after approval.
6. Keep active project state short and historical records retrievable.

The owner is the product owner and final approver. No AI has permanent arbitration authority.

## 2. Repository responsibilities

- `Misora-Editor`: application source, tests, `AGENTS.md`, `PROJECT_STATE.md`, and coding workflow.
- `Misora-Reference`: research, prototypes, source references, active debate notes, decision records, templates, and historical archives.

Do not place runtime dependencies or local game database files in the reference repository.

- `BRIEF.md` — the question, repository SHA, scope, and decision needed.
- `REVIEW_01_<name>.md` and `REVIEW_02_<name>.md` — independent first-pass reviews.
- `ADVERSARIAL_REVIEW.md` — challenges, contradictions, and missing evidence.
- `DECISION.md` — the owner's decision, accepted risks, and unresolved dissent.
- `EXECUTION_BRIEF.md` — the approved task prompt for the coding agent.
- `VERIFICATION.md` — actual commands, output, and post-change review.

These files are a recommended manual workflow, not commands automatically generated by `secretary.py`.

## 4. Evidence classification

Every important statement must be labeled:

- `SOURCE-VERIFIED`: directly supported by current code, tests, official documentation, or an observed command result.
- `REPRODUCED`: reproduced with an exact test or controlled experiment.
- `USER-OBSERVATION`: reported by the owner but not independently verified.
- `INFERENCE`: reasoned conclusion, not established fact.
- `PROPOSAL`: suggested future change.
- `UNKNOWN`: unresolved.

Use current file paths and line numbers for code claims. Cite official documentation and access dates for changing model/tool facts. A copied model answer is not a source.

## 5. Meeting procedure

### Before the meeting

1. Create a short `BRIEF.md` from `templates/DEBATE_BRIEF_TEMPLATE.md`.
2. Record target repository, branch, commit SHA, and files the reviewers should inspect.
3. Decide whether the task is low, medium, or high risk.
4. Use one or two independent reviewers initially; do not invite every available model by default.

### Independent round

Give the same brief to each reviewer separately. Require findings, source paths/lines, reproduction steps, assumptions, and unknowns. Do not share answers between them before this round is complete.

### Challenge round

Give the independent reports to one critic. Ask it to identify unsupported claims, missing cases, conflicting assumptions, and experiments that could settle disagreements.

### Decision round

Create `DECISION.md` from the template. Record accepted findings, rejected findings and why, unresolved dissent, risks, and the owner's approval. Do not demand unanimous agreement. If the evidence is insufficient, defer or run an experiment.

### Implementation handoff

Create one `EXECUTION_BRIEF.md` from the template. It must include scope, allowed/forbidden files, acceptance criteria, test commands, data preservation, rollback, and stop conditions. The owner approves it before an implementation agent edits source.

### Completion

Record the actual diff and command output. If a test could not run, say why. Do not copy historical test counts into a new verification report.

## 6. Archive policy

- Keep the concise current status and decision records easy to find.
- Preserve raw transcripts as history; do not edit a transcript to make it match the final decision.
- Move completed meeting transcripts to `archives/` when appropriate. Update archive manifest/checksums when ZIPs change.
- Verify archives with `python tools/secretary.py verify-zips`.
- Do not repeatedly compress/delete active notes during a live task. Archive after the decision or implementation milestone is closed.

## 7. `tools/secretary.py` — actual commands today

The current script supports only:

```bash
python tools/secretary.py status
python tools/secretary.py verify-zips
python tools/secretary.py ingest <path-to-transcript>
```

What they actually do:

- `status`: prints basic active-document, debate-folder, prototype, archive, and reference-toolchain status.
- `verify-zips`: tests ZIP integrity in `archives/` and `reference_toolchains/archives/`.
- `ingest`: reads a transcript, counts lines and Markdown headers, and lists short lines containing the word `LOCK` as possible keywords.

The script does not currently append AI opinions, synthesize meetings, create decisions, generate prompts, compress transcripts, delete source files, or validate technical correctness. Do not describe those as existing capabilities until code and tests implement them.

A future low-risk improvement could add a `record-opinion` command that copies a supplied response file into a dated meeting record. It should record, not interpret or approve, the content. Add that only in a separate approved coding task with tests.

## 8. Database and repository hygiene

`master.db` is not tracked in the current repository snapshot. The current metadata resolver searches local paths, opens SQLite read-only, and has fallback mappings. Keep the database external and local. Do not invent an upstream URL, size, update cadence, or legal status. The root `.gitignore` supplied with this pack excludes local DB files, Python cache, temporary files, and raw Unity assets.

A `.gitignore` does not untrack an already tracked `.pyc`; the repository currently contains a tracked file under `tests/__pycache__/`. Remove that file from the Git index in a separate reviewed cleanup task, then keep future generated bytecode ignored.

## 9. Required secretary completion report

Every finished task report should state:

1. Task and target commit SHA.
2. Files read and files not accessible.
3. Findings grouped by evidence category.
4. Decisions and remaining dissent.
5. Approved implementation brief, if any.
6. Files changed and why.
7. Exact commands/tests run and actual results.
8. Risks, blockers, and stop point.
