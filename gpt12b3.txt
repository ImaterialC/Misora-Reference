### **A. Tegaskan jumlah pembacaan file dan freshness check**

Ini adalah catatan Qwen yang saya setujui sepenuhnya.

Draft menghendaki:

- satu scan seluruh dictionary;
- pembacaan file terdampak;
- kemudian konfirmasi konflik;
- freshness check sebelum write.

Namun, draft belum menjelaskan apakah data yang sudah dibaca ketika scan akan disimpan dalam memory atau dibaca lagi ketika proses update.

Saya merekomendasikan arsitektur berikut:

**Tahap 1 — Fresh scan**

Satu traversal pada root yang telah divalidasi. Setiap eligible `.txt` dibaca dan didecode satu kali.

**Tahap 2 — Batch matching**

Buat lookup berdasarkan `norm_search()` untuk seluruh JP key yang dimodifikasi. Simpan hasil match serta konten decoded file terdampak dalam memory.

**Tahap 3 — Conflict confirmation**

Tampilkan konfirmasi konflik setelah seluruh hasil batch diketahui, bukan modal berulang untuk setiap box.

**Tahap 4 — Pre-write freshness check**

Bandingkan metadata file (`mtime_ns`, size, dan identitas file) dengan snapshot ketika file dibaca. Jika berubah selama proses konfirmasi, batalkan update file tersebut dan pertahankan box terkait untuk retry.

**Tahap 5 — Grouped atomic write**

Kelompokkan seluruh perubahan berdasarkan target file. Satu backup dan satu atomic write maksimal per file terdampak.

Dengan desain tersebut, file tidak perlu dibaca ulang hanya karena ada beberapa box yang mengubahnya.

Satu catatan presisi: metadata check tidak memberikan jaminan absolut terhadap perubahan eksternal yang sengaja mempertahankan ukuran dan timestamp file. Jika ingin jaminan lebih kuat, `/plan` harus menguraikan pilihan hash revalidation dan dampaknya terhadap read count. Jangan mengklaim jaminan absolut dari `mtime_ns`/size saja.

### **B. Kompleksitas sebaiknya ditulis lebih presisi**

Draft menyebut target `O(F+B)` atau `O(B)` via index.

Untuk satu kali traversal, yang sebenarnya harus diproses adalah jumlah baris dictionary, bukan hanya jumlah file.

Saya menyarankan target ditulis:

\\[ O(E+B+M) \\]

Dengan:

- \\(E\\): total baris dictionary yang dibaca.
- \\(B\\): jumlah box yang dimodifikasi.
- \\(M\\): jumlah match yang ditemukan.

Kuncinya adalah membangun lookup target JP key berdasarkan `norm_search()`, lalu memproses setiap baris dictionary sekali. Hindari loop yang memeriksa seluruh baris terhadap setiap JP key.

Satu traversal file tidak otomatis berarti algoritmanya sudah efisien jika masih ada nested loop \\(B \times E\\).

### **C. Perjelas hasil batch dan pelestarian&#x20;**`_modified_boxes`

Ini perlu ditambahkan, khususnya untuk dua kondisi:

**1. Same JP, different English**

Misalnya:

```
Box A:
JP = こんにちは
EN = Hello!

Box B:
JP = こんにちは
EN = Good morning!
```

Keduanya memiliki JP key yang sama menurut `norm_search()`. Sistem tidak boleh menentukan hasil berdasarkan urutan iterasi.

Rekomendasi: tandai sebagai konflik batch, jangan menulis key tersebut sebelum pengguna menyelesaikan konflik, dan jangan menghapus UID kedua box dari daftar pekerjaan yang belum tersinkronisasi.

**2. Partial file-write failure**

Misalnya ada tiga target file:

- File A berhasil ditulis.
- File B gagal.
- File C berhasil ditulis.

Jangan menghapus seluruh `_modified_boxes` hanya karena fungsi batch telah selesai mengembalikan hasil.

API batch perlu membedakan box yang berhasil, dilewati karena konflik, dan gagal akibat file I/O. Hanya pekerjaan yang benar-benar selesai yang boleh dihapus dari daftar retry.

Ini harus tetap mempertahankan `test_s2_dirty_contract::test_07`: kegagalan secondary XUAT sync tidak boleh membatalkan keberhasilan primary bundle save.

### **D. Tegaskan pemakaian strict resolver dan exclusions**

Saya setuju dengan dependency injection untuk menghindari circular import:

```
misora.py
    |
    +--> resolve_xuat_text_roots()
    |
    +--> exclusion helper
    |
    +--> XUnitySyncManager batch API
```

`core/xunity_sync.py` tidak boleh melakukan top-level import `core.xuat_index`.

Pastikan pula mekanisme DI benar-benar meneruskan aturan pengecualian yang sama, bukan hanya meneruskan daftar root yang sudah benar. File `.font.txt`, `.resizer.txt`, `Postprocessors.txt`, `Preprocessors.txt`, `Substitutions.txt`, seluruh legacy exclusions, dan `.bak_` harus diperlakukan konsisten.
